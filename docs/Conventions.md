# Конвенции кода и архитектуры (обязательны для любого кода в этом репо)

## Структура репозитория (монорепо)
```
tirestock-web/
├── CLAUDE.md, docs/
├── web/                  # Next.js витрина + админка
│   ├── app/              # роуты (App Router)
│   ├── components/       # ui/ (кнопки, поля) и blocks/ (шапка, карточка товара)
│   ├── lib/              # api-клиент (сгенерированные типы), утилиты
│   └── styles/           # токены, глобальные стили
├── api/                  # Go-сервис
│   ├── cmd/api/main.go   # единственная точка входа (http + фоновые контуры)
│   ├── internal/
│   │   ├── catalog/      # фича: каталог (handlers.go, service.go, queries.sql, sync.go)
│   │   ├── orders/       # фича: заказы + outbox (handlers.go, service.go, worker.go)
│   │   ├── content/      # фича: контент админки
│   │   ├── integrations/ # адаптеры: selecttyres/, tradesk/ (+ mock/)
│   │   ├── httpx/        # общее: middleware, ответы об ошибках, роутер
│   │   └── db/           # pgx-пул, sqlc-генерация, миграции
│   └── openapi.yaml      # контракт, источник TS-типов
└── deploy/               # docker-compose, nginx, env-примеры
```

## Go — правила
1. **Пакет = фича, не слой.** `internal/orders`, а не `internal/services` + `internal/repositories`.
   Внутри фичи файлы по ролям (handlers/service/worker), но это ОДИН пакет.
2. **Хендлеры тонкие:** распарсить → провалидировать → вызвать сервис → отдать DTO.
   Бизнес-логика только в service. SQL только через sqlc в queries.sql фичи.
3. **Интерфейсы объявляет потребитель** и только там, где есть ≥2 реализации или мок.
   Сейчас это ровно два: `CatalogSource` (selecttyres | mock) и `OrderDelivery`
   (tradesk | mock). НЕ плодить интерфейсы «на будущее».
4. Ошибки: обычные `error` + `fmt.Errorf("...: %w", err)`. Никаких паник в хендлерах,
   никаких самодельных иерархий ошибок. Sentinel-ошибки фичи — в её же пакете.
5. Контекст первым аргументом везде, где есть I/O. Таймауты на все внешние вызовы.
6. Конфиг — env-переменные, читаются один раз в main, передаются явно. Без глобалов,
   без синглтонов, без init() с побочными эффектами.
7. Зависимости: stdlib прежде всего. Новая библиотека — только если экономит >100 строк
   и у неё нет альтернативы в stdlib. Список разрешённых: chi, pgx, sqlc, golang-migrate,
   robfig/cron, jose/jwt-библиотека для админ-сессий. Остальное — спросить.
8. Outbox: заказ пишется в БД транзакционно со строкой outbox (status=pending).
   Воркер: SELECT ... FOR UPDATE SKIP LOCKED, ретраи с экспонентой, после N неудач —
   status=failed (виден в админке). Никаких сообщений «в памяти».

## API — правила
1. REST, ресурсы во множественном числе: `GET /api/v1/products`,
   `GET /api/v1/products/{slug}`, `POST /api/v1/orders`, `POST /api/v1/callbacks`.
   Версия в пути (`/v1`) с первого дня.
2. Формат ошибки един: `{"error": {"code": "string", "message": "string"}}` + верный
   HTTP-статус. Коды — стабильные строки (`validation_failed`, `not_found`), не числа.
3. Пагинация каталога: `?page=` + `?per_page=` (дефолт 24), ответ с `total`.
   Фильтры — плоские query-параметры с теми же именами, что в URL витрины
   (width, profile, diameter, season, brand, price_min, price_max, spikes, runflat).
4. Любое изменение API начинается с правки openapi.yaml, потом код. Спека — источник
   истины; CI генерит из неё TS-типы в web/lib/api/.
5. Мутации идемпотентны где возможно: POST /orders принимает клиентский
   idempotency-key (защита от даблкликов «Оформить заказ»).

## Next.js — правила
1. Server Components по умолчанию. `"use client"` — только листовые интерактивные
   компоненты (степпер, табы, дропдаун, корзина). Страницы и layout — всегда серверные.
2. Данные ходят ТОЛЬКО через web/lib/api (типизированный клиент из OpenAPI).
   Никаких fetch в компонентах, никаких прямых обращений к Postgres из Next.
3. Состояние фильтров/табов/пагинации живёт в URL (searchParams), не в useState.
   Корзина — cookie + серверное чтение, не localStorage.
4. components/ui — тупые компоненты из DESIGN_SYSTEM.md (пропсы → разметка, без данных
   и без бизнес-логики). components/blocks — составные (шапка, карточка товара),
   принимают данные пропсами. Никакой компонент не знает про источник данных.
5. Токены дизайн-системы — единожды в styles/ (CSS-переменные + конфиг Tailwind).
   В коде компонентов НЕТ сырых hex/px из головы — только токены и шкала отступов.

## Общее
- Секреты только в env; .env.example поддерживается актуальным; секреты не коммитятся.
- Миграции — единственный способ менять схему БД. Никаких правок схемы руками.
- Каждый PR/коммит проходит: `go vet` + тесты api, `tsc --noEmit` + build web.
- Тесты обязательны для: outbox-воркера, маппинга фильтров URL→SQL, адаптеров
  интеграций (против моков). UI-тесты — позже, не сейчас.
- Комментарии и названия коммитов — по-русски или по-английски, но консистентно
  внутри файла; названия в коде — английские.
